## 1. 관리자 콘솔 + 메일 발송 + 배치잡 (PR #5, #6, #7)

### 관리자 콘솔 (`/admin`, admin 전용)

`core/views/admin.html` 하나로 만든 탭형 단일 페이지. API는 전부 `core/auth-routes.js`의
`/auth/admin/*` 아래(`requireRole('admin')` 가드).

- **사용자 관리**: 계정 생성/비활성화/삭제, 앱별 접근 권한(`platform_app_grants`) 부여
- **메일 발송**: 발송 설정 상태 조회, 테스트 발송, 발송 이력 조회
- **배치잡**: 등록된 잡 목록/활성화 스위치/수동 실행/실행 이력
- **시스템 점검**: 로그인/권한 설정 상태를 한눈에 점검

### 메일 발송 (`shared/mailer.js`)

모든 앱/배치잡이 재사용하는 공통 함수: `sendMail({ to, subject, text, html, appPrefix, sentBy })`.
모든 발송 시도(성공/실패)는 `platform_mail_log`에 기록된다.

**PR #6 — IPv6 `ENETUNREACH` 방지**
Railway 컨테이너가 SMTP 호스트를 IPv6로 먼저 시도하다 라우팅이 안 돼 타임아웃 나는 문제. Node의
DNS 조회 우선순위를 IPv4로 고정해서 해결.

**PR #7 — SMTP → Brevo HTTP API 전환**
IPv6 문제를 고치고도 여전히 `Connection timeout`이 발생 → Railway 등 일부 호스팅이 아웃바운드
SMTP 포트(25/465/587/2525) 자체를 막아둔 것으로 실측 확인. HTTPS(443)로 통신하는 **Brevo REST
API**로 완전히 전환. `BREVO_API_KEY` 필요, 발신 주소는 `SMTP_FROM`(과거 SMTP 시절 변수명 유지) —
Brevo Senders에 인증된 주소여야 발송 성공.

### 배치잡 (`core/batch.js`)

`core/jobs/*.js`를 자동 스캔해 `node-cron`으로 등록. 각 파일은
`{ id, name, schedule, description, run(pool) }`을 export. 활성화 스위치는 "자동 스케줄 실행"만
제어하고, 관리자 콘솔의 "지금 실행"은 비활성 상태여도 항상 동작.

## 3. 메신저 알림 공통 모듈 `shared/notify/` (PR #8)

메일과 같은 철학(공통 발송 함수 + 항상 로그 기록)이지만, **다중 수신자 + 카테고리 기반 구독**이
추가된 구조.

```
Recipient(수신자, self/family/friend)
  └─ Channel(텔레그램/디스코드/ntfy/웹푸시 — 수신자 1명당 여러 개 연결 가능)
Category(어느 프로젝트의 어떤 알림인지)
  └─ Subscription(수신자가 어떤 카테고리를 어떤 채널로 받을지)
```

프로젝트 사용법:
```js
const notify = require('../../shared/notify');
await notify.registerCategory('camp-check', '캠핑 체크리스트', '/campchecklist'); // 1회, 멱등
await notify.send({ category: 'camp-check', title: '캠핑 3일 전!', body: '텐트 챙기셨나요?' });
```

채널 어댑터는 플러그인 구조(`shared/notify/channels/<name>.js`, `{ name, send(config, {title, body, url}) }`).
텔레그램은 `TELEGRAM_BOT_TOKEN`(전역), 디스코드는 수신자별 webhook URL, ntfy는 기본 공개 서버
사용. 관리자 콘솔에 "알림" 탭이 추가되어 수신자/채널/구독을 관리한다.

## 4. 웹푸시와 VAPID (PR #10 ~ #14)

### VAPID가 뭔가

**VAPID**(Voluntary Application Server Identification, RFC 8292)는 웹 푸시를 보낼 때
"이 서버가 누구인지"를 브라우저의 푸시 서비스(Chrome→Google FCM, Firefox→Mozilla 등)에게
증명하는 표준이다.

- 서버가 **P-256 곡선(secp256r1/prime256v1) EC 키쌍** 하나(공개키/개인키)를 미리 만들어둔다
  (`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`).
- **구독 시점**: 브라우저에서 `pushManager.subscribe({ applicationServerKey: 공개키 })`를
  호출하면, 그 구독(endpoint)이 **이 공개키에 영구적으로 묶인다**. 이후 그 서버(같은 개인키를
  가진 서버)만 이 구독으로 푸시를 보낼 수 있다.
- **발송 시점**: 서버가 개인키로 JWT를 서명해서 `Authorization` 헤더에 담아 보낸다. 푸시
  서비스가 그 서명을 구독에 묶인 공개키로 검증해서, 구독을 만든 바로 그 서버가 보낸 게 맞는지
  확인한다. `VAPID_SUBJECT`(mailto: 또는 https: URL)는 문제 생겼을 때 푸시 서비스가 서버
  운영자에게 연락할 수 있는 연락처.
- 이 구조 덕분에 서버가 각 푸시 서비스(FCM, Mozilla 등)에 개별 가입/인증할 필요 없이, 자기
  키쌍 하나로 모든 브라우저에 푸시를 보낼 수 있다.

**핵심 함의**: 공개키가 바뀌면(=키를 재발급하면) 그 이전에 만들어진 모든 구독은 새 키와
매칭되지 않아 즉시 무효가 된다 — 반드시 새 키로 **재구독**해야 한다.

## 5. 다중 기기 발송 + 셀프서비스 "내 알림 설정" (PR #15)

### 다중 기기 웹푸시 발송

한 수신자가 PC/모바일 등 여러 기기에서 각각 구독해도, 기존엔 DB 조회가 `getChannelConfig`
(단수, `LIMIT 1`)라 **가장 최근에 구독한 기기 하나만** 실제로 알림을 받고 있었다.

- `getChannelConfig` → `getChannelConfigs`(복수, 활성 상태 전부를 반환)로 교체
- 발송 로직도 `sendToChannel`이 그 채널의 활성 연결 **전부**에 `Promise.allSettled`로 병렬
  발송 후 `{ sent, failed, total }`을 집계 — 기기 하나가 죽어있어도(자동 비활성화 포함) 나머지는
  계속 시도되고, 전부 실패했을 때만 에러로 처리.

### 셀프서비스 "내 알림 설정" (`/notify-settings`)

지금까지 알림 채널/구독 관리는 관리자 콘솔에서만 가능했다. 이번에 **로그인한 사용자 누구나**
(admin 권한 불필요) 본인 알림을 스스로 관리할 수 있는 페이지를 추가했다.

- `notify_recipients.platform_user_id`로 플랫폼 계정과 1:1 연결(`ON DELETE SET NULL` — 계정
  삭제 시 recipient 자체는 남고 연결만 끊김)
- `getOrCreateRecipientForUser(platformUserId, name)` — 로그인 사용자 ↔ recipient 자동 매핑
  (멱등)
- `deleteChannelIfOwned` — 본인 채널만 삭제 가능하도록 소유권 체크(다른 사용자 채널 id로
  삭제 시도 시 404로 차단)
- 라우트: `core/auth-routes.js`의 `/auth/notify/*` (admin 전용 `/auth/admin/notify/*`와는
  분리된 별도 그룹, `requireLogin`만 필요)
- 화면: `core/views/notify-settings.html` — 본인 채널 연결/삭제, 카테고리별 채널 선택 구독,
  이 브라우저 웹푸시 구독, 테스트 발송, 본인 발송 로그
- 허브 페이지(`/`)에 "🔔 알림 설정" 링크 추가(모든 로그인 사용자에게 노출)

### 향후 확장 패턴 (아직 미사용)

다른 프로젝트가 참여자에게 알림을 보내고 싶을 때도 같은 패턴을 그대로 쓸 수 있다:

```js
const notifyDb = require('../../shared/notify/db');
const notify   = require('../../shared/notify');

const recipient = await notifyDb.getOrCreateRecipientForUser(participantPlatformUserId, name);
await notify.send({ category: 'camp-check', recipientIds: [recipient.id], title, body });
```

예: campchecklist가 트립 참여자들에게 "내용 등록해주세요" 알림을 보내는 기능 — 아직 구현되지
않았고, 이 패턴만 준비되어 있다. 로그인 계정이 없는 가족/지인은 이 방식을 못 쓰므로 여전히
관리자 콘솔에서 수동으로 채널을 등록해야 한다.

## 6. 환경변수 (신규/변경분만)

| 변수 | 기본값 | 용도 |
|---|---|---|
| `BREVO_API_KEY` | (없음) | 메일 발송(Brevo API) |
| `SMTP_FROM` | `SMTP_USER` 값 | 발신 주소 (Brevo Senders에 인증된 주소여야 함, 변수명은 과거 SMTP 시절 그대로 유지) |
| `TELEGRAM_BOT_TOKEN` | (없음) | 텔레그램 알림 채널 |
| `VAPID_SUBJECT` | (없음) | 웹푸시 VAPID JWT의 연락처(mailto: 또는 https:) |
| `VAPID_PUBLIC_KEY` | (없음) | 웹푸시 VAPID 공개키 — 반드시 P-256 곡선 키, 브라우저 구독에 그대로 사용됨 |
| `VAPID_PRIVATE_KEY` | (없음) | 웹푸시 VAPID 개인키 — 발송 시 JWT 서명에 사용, 외부 노출 금지 |

`node -e "console.log(require('web-push').generateVAPIDKeys())"`로 VAPID 키쌍 생성.
**키를 재발급하면 그 전에 만들어진 모든 웹푸시 구독이 무효가 되므로, 재발급 후에는 사용자들이
"내 알림 설정" 또는 관리자 콘솔에서 재구독해야 한다.**
